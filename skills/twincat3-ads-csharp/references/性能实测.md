# ADS 性能实测（本机回环 + 跨网线）

> 正文 §八 只留选型结论，这里放完整数据与出处。
> 数字分两类：**实测**（生产项目样本 / 独立 demo）和**估算**（跨网线大数据），后者会明确标注。

## 一、单次往返（p50，生产项目样本实测）

| 操作 | 跨网线 | 本机回环 |
|---|---|---|
| 同步读 BOOL / LREAL | 2.87 / 3.01 ms | **1.07 / 1.06 ms** |
| 同步写 UDINT | 3.14 ms | 1.07 ms |
| 并发 200 均摊 | 0.222 ms | **0.043 ms** |
| 连接建立 | 31.6 ms | 37.1 ms |

- **BOOL 和 LREAL 一样快** → 开销是**固定的协议往返**，与数据量无关
- **写 → 读到** = 两次往返 ≈ 6.4ms（连续 100 轮 p50 7.2ms，200/200 一致）

## 二、轮询 vs 通知（156 变量 / 50ms 一轮 / 26 秒，生产项目样本实测）

| 方式 | 请求/秒 | 上位机 CPU | PLC CPU |
|---|---|---|---|
| 通知 | 0.3 | **0.2%** | +2% |
| **批量读**（Sum 打包） | **19** | **2.7%** | +2% |
| 并发读（一个个甩） | 2500 | **33.5%** | +11% |

→ **"轮询吃 PLC"完全是"并发"造成的**：要轮询就用批量读，绝不要并发
（请求数少 133 倍、上位机 CPU 只有 1/12）。

## 三、三种访问方式（独立 demo，本机回环，2026-10-18）

同一变量 `MAIN.A`（BOOL），每项 500 次：

| 方式 | 读 (ms) | 写 (ms) |
|---|---|---|
| **裸符号名** `ReadValue("MAIN.A", ...)` | **3.72** | **3.39** |
| 句柄 `CreateVariableHandle` + `ReadAny` | 1.22 | 1.21 |
| 内存 `Read(0x4021, 位地址, buf)` | 1.32 | 1.20 |

- 符号名的解析成本 ≈ **2.4ms/次**；句柄只付一次（建句柄那两次往返）
- **内存寻址 vs 句柄：没有可测差异**（同一 API `Read(IG,IO,buf)` 下 1.20 vs 1.25；
  1KB 1.18 vs 1.27；1MB 2.15 vs 2.24 —— 差值在噪声内）
- **"内存最快"只在对比裸符号名时成立**；对句柄没有优势，因为瓶颈是往返，不是寻址

### 一个容易踩的测量陷阱

`ReadValue` 会**复用已存在的句柄**（不会自己建）。所以：
- 先建句柄再测 `ReadValue` → 测出来和句柄一样快（1.0x 假象）
- 正确顺序：**先测裸符号名（零句柄），再建句柄测**（复现工具：`scripts/ads-speedtest`）

### 整数组/结构体句柄（本机，2026-10-19）

同一结构体数组 `MAIN.arrSt`（2448B，`ARRAY[1..3] OF stAxisInput`），每项 200–500 次：

| 方式 | 读 | 写 |
|---|---|---|
| **整变量句柄** | **1.246–1.286ms** | **1.488ms** |
| 内存 | 1.139–1.357ms | 1.123ms |
| 符号名 | 1.248–1.381ms | — |

→ 整变量句柄与内存**同档**；大数组/结构体优先用“整变量句柄 + `Read(0xF005,h,buf)`”，
不需要内存法。`ReadAny<byte[]>` 不行（长度未知）。

## 四、数据量（独立 demo，本机回环，3–5 轮中位数）

| 数据量 | 读 | 写 | ADS 往返 |
|---|---|---|---|
| 1 KB | ~1.3 ms | ~1.4 ms | 1 |
| 100 KB | ~1.4 ms | ~1.4 ms | 1 |
| 500 KB | ~1.4 ms | ~1.9 ms | 1 |
| 1 MB | ~2.2 ms | ~2.5 ms | 1 |
| 2 MB | ~3.0 ms | ~3.5 ms | 1 |

- **ADS 单次请求不分包**：测到 **2MB 仍是 1.0 个往返**（用 `TotalCycles` 直接计数）。
  分包发生在 **TCP 层**（100KB ≈ 70 个 TCP 段），对应用透明。
- **写比读先变慢**：≤100KB 读写都平稳；>100KB 写开始波动上升（~15–30%），读到 500KB 仍基本不变。
  ⚠ 1–100KB 之间的差异在噪声内 —— **"100KB 拐点"是"波动开始变大"，不是硬台阶**。
- 拟合（本机）：`总耗时 ≈ 1.2ms（固定往返）+ 数据量 / ~1 GB/s`

## 五、本地连接也走 TCP 环回（netstat 实测）

`Connect(851)` 会建立：

```
TCP 127.0.0.1:<临时端口> ↔ 127.0.0.1:48898   ESTABLISHED
```

所以**本机 1.2ms 往返里包含完整的 TCP 协议栈开销**（不是"内存里走所以接近 0"）；
只是物理介质是内存（~1 GB/s），不是网线。

## 六、跨网线（估算，非实测）

公式：`≈ 3ms（固定往返，弯管实测 2.87–3.14ms）+ 数据量 / 带宽`

| 数据量 | 千兆（~100 MB/s） | 百兆（~12 MB/s） |
|---|---|---|
| 1 KB | ~3 ms | ~3 ms |
| 100 KB | ~4 ms | ~11 ms |
| 1 MB | ~13 ms | ~85 ms |
| 2 MB | ~23 ms | ~160 ms |

→ **大块传输只在本机快；跨网线单次别超过几十 KB。**

> 边界：大数据跨网线**没有实测过**（手边没有第二台 PLC）。网络部分是"固定往返（实测）+ 带宽（理论）"的估算。

## 七、Sum 批量上限（独立 demo，本机回环）

用 `MAIN.arrSum[1..N]` 的每个元素当一个独立变量 —— 在 ADS 层与"真声明 N 个变量"**等价**
（每个元素有独立 `InstancePath`、独立句柄），但**不吃 TC3 的声明/编译/符号表开销**。

> ⚠ **句柄数上限（2026-10-20 实测复核）**：本机 TwinCAT 3.1.4024.75 上限 **10000**；
> 现场 CX5230（3.1.4024.65）上限 **2000**。超过上限时 `SumCreateHandles` **不报错**，
> 超出部分直接返回 `0` 句柄；读写这些 0 句柄报 `DeviceSymbolVersionInvalid`。
> **下面旧表没有检查 0 句柄**：N=8000 有效；**N=12000 / 16000 / 20000 只有前 10000 有效，
> 对应的读/写耗时不可用**。

| N | 建句柄 | 读 | 写 |
|---|---|---|---|
| 8000 | 39.4 ms | 19.3 ms | 12.8 ms |
| ~~12000~~ | 作废（超上限）| — | — |
| ~~16000~~ | 作废（超上限）| — | — |
| ~~20000~~ | 作废（超上限，有效 10000）| — | — |

- **本机上限 10000**；N=20000 时只有前 10000 有效（旧结论“全成功、上限没到”错误）
- **读耗时几乎不随 N 增长**（8000 与 20000 都 ~19ms）—— 开销主要在固定部分（往返 + 编组框架），
  子命令的边际成本很低
- 理论上限估算：`ADS 单次请求上限 / 每个变量约 13 字节`；测到 2MB 请求可行 → **约 16 万**（未验证）
- 对比**内存一次读写 8KB**：读 1.38ms / 写 1.27ms —— **连续数据用内存方式快一个数量级**
  （Sum 8000 个：读 18.2 / 写 7.2ms；数据只有 7.8KB，慢在子命令处理，不在数据量）

### 子命令数的影响（数据量固定 20000 字节，本机回环）

全部走内存寻址 `0x4020`，只把 20000 字节拆成不同块数：

| 分块 | 子命令数 | 读 | 写 |
|---|---|---|---|
| 1 × 20000 | 1 | 1.096 ms | 1.221 ms |
| 10 × 2000 | 10 | 1.313 ms | 1.254 ms |
| 100 × 200 | 100 | 1.377 ms | 1.314 ms |

- **100 个子命令只比 1 个慢 0.28ms**（每个约 2.8µs）—— 微秒级，不构成瓶颈
- 写更不敏感（+8%）
- 对比：**20000 个子命令**（每块 1 字节）→ 18.9ms —— 子命令成本要到**上千个**量级才明显
- 实际项目（弯管 163 个变量）完全在这个"可忽略"区间

### ★ 释放 Sum 创建的句柄：必须用 `SumReleaseHandles`

```csharp
new SumReleaseHandles(client, handles).ReleaseHandles();
```

逐个 `DeleteVariableHandle(h)` 删 Sum 创建的句柄会抛 **`AdsErrorException 0x710 (Symbol could not be found)`**，
而且删不干净 → 后续批次复用旧句柄、**测出来的数据偏乐观**（实测踩到）。

## 八、现场实测（跨网线，2026-10-19）

**环境**：现场 PLC `<target-net-id>:851`，TwinCAT **3.1.4024**（x64，符号表指针 8B），
测试程序 `AdsTest`（PlcTask 10ms / 优先级 21），上位机通过局域网连接。

### 8.1 单次时延

| 路径 | 实测 |
|---|---:|
| 符号名读（无缓存句柄） | **9.175 ms** |
| 句柄读 | **2.826 ms** |
| 符号名读（句柄缓存命中） | 2.955 ms |
| `ReadAny(path,type)`（0xF004） | 3.036 ms |
| 内存读（0x4020 + 偏移） | 3.119 ms |

跨网线单次往返约 **2.8–3.1ms**，和本机回环的 1.1–1.3ms 差距就是网络往返。

### 8.2 单连接顺序轮询：上限 ~320/s

按目标速率逐步加载（每档 3 秒，单变量 `GVL_AdsDemo.lrReal`，句柄读）：

| 目标 | 实际 | 错误 | p50 | p95 | p99 |
|---:|---:|---:|---:|---:|---:|
| 10/s | 10.3/s | 0 | 3.27ms | 4.15ms | 5.26ms |
| 300/s | 290.6/s | 0 | 2.83ms | 3.88ms | 4.48ms |
| 400/s | **320.1/s** | 0 | 3.14ms | 4.01ms | 4.46ms |
| 500/s | **324.2/s** | 0 | 3.16ms | 4.06ms | 4.44ms |

**目标 400/500 都只跑到 ~320/s**，单次时延不变 —— 上限 = `1 / RTT ≈ 1 / 3ms ≈ 330 次/秒`，
再提高目标速率只会空等，吞吐不会增加。

| 10 | 2.735ms | 365.6 | 3,656 | 48 |

| 50 | 4.055ms | 246.6 | 12,329 | 49 |
| 100 | 3.859ms | 259.1 | 25,910 | 47 |
| 200 | 3.313ms | 301.8 | 60,366 | 45 |
| 500 | 3.198ms | 312.7 | 156,334 | 32 |
| 1000 | 4.736ms | 211.2 | 211,153 | 46 |
| 2000 | 5.770ms | 173.3 | 346,616 | 41 |
| ~~5000~~ | 作废（超上限）| — | — | — |
| ~~7500~~ | 作废（超上限）| — | — | — |

- **N ≤ 2000 的数据有效**：N=2000 时 5.77ms / 34.6 万变量/s

### 8.4 单变量大块读写（现场）

对象 `MAIN.arrSum`（`ARRAY[1..2000000] OF BYTE`，内存寻址，写回原内容不改数据）：

| 数据量 | 读 | 写 |
|---:|---:|---:|
| 1 KB | 2.984 ms | 3.160 ms |
| 10 KB | 3.621 ms | 3.043 ms |
| 50 KB | 3.836 ms | 4.155 ms |
| 100 KB | 5.935 ms | 5.670 ms |
| 200 KB | 9.737 ms | 7.266 ms |
| 300 KB | 12.929 ms | 8.927 ms |
| 500 KB | 21.435 ms | 13.489 ms |
| 750 KB | 34.677 ms | 18.741 ms |
| 1 MB | 46.855 ms | 25.799 ms |
| 2 MB | 89.291 ms | 42.359 ms |

- 拟合：`读 ≈ 3ms + 数据量 / ~24 MB/s`（≈190 Mbit/s）；
  `写 ≈ 3ms + 数据量 / ~48–50 MB/s`（≈390–400 Mbit/s）
- 1KB 时就是一次往返；100KB 以后线性增长
- **现场读写明显不对称，写约为读的 2 倍**（2MB：读 89ms / 写 42ms），
  各数据量上都成立；原因未解释，只记录事实
- 对比本机：**小数据（≤100KB）读写基本一致**（1KB–20KB 实测 1.15–1.29ms，差 <0.1ms）；
  **大数据写略慢 15–30%**（2MB：读 3.0ms / 写 3.5ms）。
  → “写比读快 2 倍”**不是 ADS 通用规律**，是现场这条路径的特性
- 本机回环是 `1.2ms + 数据量 / ~1 GB/s`（内存介质），**不能代表现场**
- 写路径能到 ~49 MB/s → **链路至少 ~400 Mbit/s**；若现场是千兆，
  读路径的瓶颈更可能在 ADS/PLC 读方向，而不是网线（未核实网卡/交换机）
- 结论：**跨网线单次别带太大块**；几十 KB 以上就要按毫秒级预算，2MB 已是百毫秒级

### ⚠ 事故记录：2,097,152B 打停现场控制器（2026-10-19）

- 测试尺寸写成 **2,097,152B（2MiB）**，但 `MAIN.arrSum` 只有 **2,000,000B**
  → **越界 97,152B，覆盖了 `MAIN.ST1` / `MAIN.arrSt`**（都在 MArea 内）
- 2,097,152B 正好是 **AMS 路由器默认 2048kB**；加上 ADS/AMS 头就超过路由器缓冲
- 连续 **20 次 2MB 读 + 20 次 2MB 写**后：
  **控制器直接故障（红）/瘫痪**，851 和系统服务 10000 全部 `0x745`；
  **需要现场断电重启**才恢复（重启后 PLC 变量回到默认值）
- **硬结论**：
  1. **单次 ADS 传输保守 ≤1MB；绝不低于 2,048kB 的安全余量**
  2. **测试尺寸必须 ≤ 符号 `ByteSize`**，否则会覆盖相邻变量
  3. 大块必须**分段**，不要反复整块读写
- **根因待确认**：越界是事实（覆盖 `ST1`/`arrSt` + 填充，全部在 MArea 内）；
  但第一次 2MB 写就已经越界却没事，故障发生在**连续 2MB 传输之后**，
  且 2,097,152B 正好顶到 AMS 路由器 2048kB。**直接触发更可能是路由器/大包**；
  要分离需要控制器日志，或做“**不越界的 2,000,000B**”对照实验（从 ≤1MB 起逐步加）
- 工具已加硬保护：超过符号大小直接拒绝；>1MB 默认拒绝，需显式 `--allow-large`（仍禁止 >2,000,000B）

**复现对照（2026-10-19，不越界）**：

- `2,000,000B × 20 读 + 20 写`（plain bench，非 AsResult）
- 读 **99.900ms/次**，写 **47.426ms/次**
- 跑完 851/10000 均 Run，`MAIN.ST1.lSetPos1` 仍为 10（未被覆盖）
- → **单次 20+20 的非越界 2,000,000B 传输可承受**；
  故障更可能与“越界 + 累计约 160MB + 第二步 AsResult”的组合有关，尚未完全分离
- **2026-10-19 决定：不再在现场做第二步对照**（避免再次打停控制器）；
  根因保留为“待定”，如需分离应在实验室/备用控制器上做

### 8.6 通知（现场）

- `notify GVL_AdsDemo.bHeartbeat 2`（100ms 方波，`cycleTime=0`）→ **2 秒 40 条**
  → Ex 通知在现场网络下可用，边界/周期符合预期
- **2026-10-21 现场 CX5230（AdsTest，1ms 任务，`MAIN.bFastToggle`，cycleTime=0）**：
  3 秒 **3001 条**，平均 **1.000ms**；到达间隔 p50 **1.07** / p90 **1.68** / p99 **2.39ms**（max 5.56）
  - 按 0.1ms 划批 → **约 2474 批、1.21 条/批**：约 80% 的交付只有 1 条，约 20% 是 2 条一起到
  - 对照：本机（250µs 任务）是强攒批 ~4 条/批；**现场链路攒批轻得多，但尾部抖动更大（2~5ms）**
  - `OnChangeInContext`（ContextMask=0）与 `OnChange` 分布一致
- **同日现场 0.5ms 任务复测**（同一变量/配置）：3 秒 **6003 条**，平均 **0.500ms**；
  p90 1.40 / p99 2.06ms；按 0.1ms 划批 → **2502 批、2.40 条/批**，**批间 ~1.2ms**
  —— 与 1ms 任务时的 1.21ms/批相同 → **任务加快只增加每批样本数，不改交付节拍**。
- **同周期内多次变化是否通知（2026-10-21，现场 0.5ms 任务）**：
  程序改成 `bFastToggle := NOT bFastToggle; 记录中间值; bFastToggle := NOT bFastToggle;`
  （一个周期内 `+ → − → +`，净变化为零）→ 3 秒 **0 条**通知（注册时那 1 条除外）。
  中间值确实出现过（`SEL` 捕获到 True，说明第 1 次翻转生效）→
  **ADS 只在任务周期结束时比较一次内存值，中间变化不通知**；
  窄于任务周期的脉冲对 ADS 完全不可见，要抓就在 PLC 侧锁存。
- **同周期内“先变/后变”的时间戳对比（2026-10-21，现场 0.5ms 任务）**：
  `MAIN.bFastToggle` 在程序第一行翻转、`MAIN.bEndToggle` 在最后一行翻转；
  两者通知的 PLC 时间戳**完全相同**（6005/6015 精确匹配，各自间隔严格 500µs），
  到达顺序是顶部先、尾部后（同一批内）。
  → **通知时间戳 = 任务周期时间，不是变量写入时刻**，同周期内的先后/耗时无法从通知分辨。
  PLC 侧用 `F_GetSystemTime()` 在首尾各记一次，`nGap` 恒为 **0** → 该函数按周期刷新，也测不了周期内差值。
- **20ms 任务 + 10ms 定时器翻转（2026-10-21，现场）**：`TON(PT:=T#10MS)` 的 Q 上升沿翻转变量，
  实际翻转间隔 **≈60ms（3 个任务周期）**——TON 需要 1 个周期累积到 10ms，Q 真后续 1 个周期复位；
  `cycleTime=0` 通知 3 秒 **50 条**、间隔 ~60ms、**一条一批、无丢失**。
  → **变量变化频率的上限就是任务周期**，小于任务周期的定时器会被量化；通知忠实反映 PLC 实际变化。
- **2026-10-21 现场同变量“直接读”对照**：句柄读 200 次（背靠背），
  p50 **3.01ms**（min 1.55 / p90 3.46 / p99 4.51），实际间隔均值 2.98ms —— 等于 RTT 下限。
  2 秒内 PLC 翻转约 **2000 次**，而固定周期轮询看到的变化次数：
  **4ms → 186、5ms → 251、6ms → 123、10ms → 87**。
  → 直接读只能拿“读到那一刻的快照”，**追不上 1ms 的变化**；要变化必须用通知。
- **未在现场重测**：结构体整块订阅（816B）、大量变量（156+）通知负载、PLC 重下/休眠后的
  通知失效与自愈。这些结论来自本机与生产项目样本（见 §4 与 `结构体.md`）

### 8.7 通知交付节奏（本机，2026-10-21）

**环境**：本机 TwinCAT 运行时，`AdsTest_PlcTask`；`MAIN.bFastToggle` 每个任务周期翻转；
`NotificationSettings(OnChange, cycleTime=0, maxDelay=0)`；每次采 3 秒。

| 任务周期 | 客户端 | 收到条数 | 平均到达间隔 |
|---|---:|---:|---:|
| 500µs | .NET `AdsClient` | 6006 | 0.500ms |
| 500µs | 原生 `TcAdsDll` | 6003 | 0.500ms |
| **250µs** | .NET `AdsClient` | **12009** | **0.250ms** |
| **250µs** | 原生 `TcAdsDll` | **12007** | **0.250ms** |

**250µs 的到达间隔分布**（.NET / 原生）：

| 间隔 | .NET | 原生 |
|---|---:|---:|
| <0.1ms | 8962 | 9079 |
| 0.1~0.25 | 163 | 1 |
| 0.25~0.75 | 641 | 627 |
| 0.75~1.5 | 2018 | 2083 |
| 1.5~3 | 221 | 216 |
| p50 / p99 | 0.008 / 1.663ms | 0.005 / 1.639ms |

- **生成端**：每条通知自带的 PLC 时间戳严格按任务周期递增（500µs 或 250µs），值 True/False 交替，一条不缺
- **交付端**：成批回调，**约 1ms 一批**（0.5ms 任务约 2 条/批，0.25ms 任务约 4 条/批）；
  攒批节拍**不随任务周期变**
- **两个独立客户端（.NET 库 / 原生 DLL）分布一致** → 攒批在**客户端 API 以下**
  （PLC 通知发送或本机 AMS 路由，未进一步定位）
- **结论**：`平均间隔`只是吞吐；单条实际到手时间 = 生成 + 排队到下一批，p99 约 1.7ms。
  要确定性延迟只能用 Sum 轮询
- 测量工程（临时）：`%TEMP%\ads-notify-rate`（.NET）、`%TEMP%\ads-native-notify`（原生 P/Invoke）
- **原生 `AdsNotificationHeader` 在本机 x64 DLL 里按 4 字节对齐**：
  `hNotification(4) + nTimeStamp(8) + cbSampleSize(4) + data[]`（data 偏移 **16**，
  不是按 8 字节对齐的 20）—— 按 8 字节读会把时间戳读成常数

### 8.8 通知时延：PLC 时间戳 vs 本机接收时间（本机，2026-10-22）

**方法**：本机 TwinCAT（`AdsTest`，1ms 任务），`MAIN.bFastToggle` 每任务周期翻转，
`cycleTime=0` 订阅；回调里用 `GetSystemTimePreciseAsFileTime` 取本机精确 UTC，
与 `e.TimeStamp`（UTC）相减。采 10 秒，**10003 条**。

**发现**：

- **PLC 时间戳与本机时钟不是同一个时基**：原始差（本机接收 − 时间戳）约 **−20ms**，
  且以 **约 −74µs/s 漂移**（10 秒漂 0.75ms）→ **直接相减不能当时延用**，必须先去掉时钟偏差/漂移。
- **分窗去漂移**（每 100ms 窗取最小值归零）后的**相对时延**：

  | 指标 | 值 |
  |---|---:|
  | p50 | **449µs** |
  | p90 | **1000µs** |
  | p99 | **1531µs** |
  | max | 6.5ms |

  （101 个窗；与 §8.7 的“约 1ms 一批”一致——时延主体是链路的攒批/派发）
- **边界**：这是**相对**时延（窗内最快一条归零）；最快的真实传输/派发耗时无法从单一时间源分离，
  **绝对值是下限**。要绝对时延需要独立的时钟同步（例如写响应 + 通知回推的往返标定），单靠时间戳相减做不到。
- PLC 时钟漂移确实存在（本机约 74ppm），跨天会累积到秒级。

**工具**：`%TEMP%\ads-notify-latency`（参数：`local` 或 NetId，符号，秒数）

## 九、这些数字对生产意味着什么

以生产项目样本的实际需求为准：**163 个变量 / 50ms 一轮**。

| 方式 | 请求/秒 | 变量/秒 | 对照测试上限 |
|---|---:|---:|---|
| 逐变量轮询 | 163 × 20 = **3,260/s** | 3,260 | ❌ 超过单连接 ~320/s 的 **10 倍** |
| Sum 批量（163 子命令） | **20/s** | 3,260 | ✅ 远低于 320/s；变量吞吐也远低于 60 万/s |

- **峰值数字（Sum 5000/7500、60 万变量/s、2MB 大块）远超正常需求**；
- 真正会碰到的边界是 **单连接 ~320 请求/秒** —— 它直接决定“**必须 Sum，不能逐变量轮询**”；
- 正常数据是 KB 级，不会碰到 2MB 路由器上限；大块必须分段；
- 性能测试的价值是**确认余量、找到失败边界**，不是追求峰值；
- 本次事故也说明：**测试一旦超出运行包线（2MB/路由器上限），会付出真实代价**。
